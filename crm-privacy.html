Privacy Policy

Favze Digital Marketing, LLC — Favze CRM — Last updated November 2026

Who This Applies To

This policy covers team members and authorized users of the Favze CRM: the internal platform used by Favze Digital Marketing employees, contractors, and collaborators. If you are a client accessing the Favze Client Portal, a separate privacy policy applies there.

What the CRM Stores

The CRM stores business operational data necessary to run Favze's services. This includes:

  • Contact and company records (names, emails, phone numbers, notes)
  • Deal and project records and associated communications
  • Internal tasks, reminders, and workflow entries
  • Campaign and email marketing records
  • Time-off requests, HR records, and payroll data entered by authorized team members
  • User account information (name, role, profile photo) for CRM users
  • Activity logs generated by CRM usage (views, edits, searches)

How Data Is Stored

CRM data is stored in two places:

  • Supabase (cloud database): the primary store for all CRM data. Supabase is hosted on AWS and uses row-level security so each authenticated user can access only the data their role permits. Data is encrypted at rest and in transit.
  • Browser local storage: a local copy of your data is kept in your browser for offline access. This copy is private to your device and browser.

Access and Authentication

Access to the CRM requires authentication. Passwords are hashed and never stored in plaintext. Microsoft Entra ID (Single Sign-On) is available and adds an additional layer of identity verification. Session tokens expire automatically after inactivity.

Account creation requires approval by the CRM administrator. Users can only access data within the permissions assigned to their role.

Third-Party Services

The CRM integrates with or relies on the following third-party services:

  • Supabase: database and authentication (supabase.com)
  • Microsoft Entra ID / MSAL: optional Single Sign-On
  • Google Fonts: typeface delivery (fonts.googleapis.com)
  • Tally: form submissions and lead capture (if relay is configured)

Each service is bound by its own privacy policy. Favze does not sell data to any third party.

Your Rights

Team members can request to view, correct, or delete their personal data stored in the CRM. To make a request, contact Riley Catalano directly. Requests will be honored within a reasonable timeframe and subject to any legal retention obligations.

When a team member departs, their user account is deactivated. Data they created in the CRM is retained as part of business records unless a specific deletion request is made.

Known Security Limitations

These are real gaps in the current implementation. We document them here so the team understands the risk posture honestly.

All CRM data lives in your browser

Contacts, deals, notes, and activity logs are stored in localStorage in each browser. Anyone with physical access to an unlocked browser session can open DevTools, call localStorage.getItem('favze_crm'), and export every record as plain JSON in under ten seconds. No additional authentication is required to do this.

The entire data model is readable in app.js

Because this is a static GitHub Pages site, the full application code including all field names, data structures, Supabase project URL, and publishable key is publicly accessible. Anyone can inspect app.js to understand exactly what the CRM stores, how auth works, and how sync is structured. This is not secret.

Limited brute-force protection on sign-in

The sign-in screen locks out an email address for 5 minutes after 5 failed attempts (client-side). Supabase server-side rate limiting is not yet enabled, so this lock applies per-browser only and does not block attempts from other devices or direct API calls. Enabling server-side rate limiting in Supabase Auth settings would close this fully.

No multi-factor authentication

Sign-in requires only email and password. If a password is guessed, reused from another breach, or phished, there is no second factor to block access. Supabase supports TOTP-based MFA; it is not currently enforced.

No Content Security Policy

GitHub Pages does not support custom response headers, so there is no CSP header on any CRM page. If a cross-site scripting vector were introduced via a note, contact field, or template, the browser would execute it with no policy-level block. All user-generated content currently runs through an esc() function before being written to the DOM, which mitigates this risk, but the absence of a CSP as a defense-in-depth layer is a real gap.

MSAL token scoped to session

The Outlook integration now stores Microsoft authentication tokens in sessionStorage rather than localStorage, so the token is cleared when the browser tab closes. Physical access to an unlocked, open tab still exposes it until the tab is closed or the session expires.

Idle sessions auto sign out

The CRM now signs out automatically after 30 minutes of inactivity. CRM data still lives in localStorage and can be read directly via DevTools even after sign-out. Do not use the CRM on shared or public machines.

Clickjacking is mitigated but not fully blocked

The CRM now includes a JavaScript framebusting snippet that breaks out of any iframe or attempts to hide the page if it detects it is being framed by another site. Because GitHub Pages does not support the X-Frame-Options or frame-ancestors CSP header, JS-based framebusting is the only available control and can be bypassed by a determined attacker. A server with custom response headers would close this fully.

External links use noopener/noreferrer

All links and media that open in a new tab now include rel="noopener noreferrer", which prevents the opened page from accessing or redirecting the CRM window via window.opener (reverse tabnapping). Links to platforms like LinkedIn, Twitter, or Facebook that the CRM constructs dynamically are validated to require an https:// scheme before being opened, preventing javascript: URI injection.

Avatar and logo images are validated before rendering

Profile avatars and company logos stored in localStorage as data URIs are now validated to confirm they are image data (png, jpeg, gif, webp, or svg) before being rendered in src attributes. A tampered localStorage entry with a non-image data URI will not render. Because localStorage is writable from DevTools by anyone with physical access to the browser, this is a defense-in-depth measure rather than a full mitigation.

These limitations reflect the current phase of the product. Moving core data to a server-side store with proper session management and enforcing MFA would close most of them. Until then, keep this CRM on personal, password-locked machines only.
